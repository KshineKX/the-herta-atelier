# 源码、安装包与实机的职责

版本号以根 package.json 为源，`node tools/set-version.mjs <版本>` 同步包元数据、锁文件和文档中的源码版本块；构建再生成客户端版本常量。verify 会拒绝版本漂移。历史日志中的版本号保留，不强行改成当前版本。

| 对象 | 用途 | 是否可作为新版本发布源 |
|---|---|---|
| 干净 Git 提交 | 唯一的开发与审查基线 | 是，记录 commit 与 tree |
| 独立冻结目录 | git archive 的确切快照，执行构建与测试 | 只可来自上述提交 |
| 预构建 ZIP | 用户安装输入，附完整清单、SHA-256 和验证回执 | 不能反向覆盖源码 |
| 用户数据目录的 versions / motion | 已安装运行文件及当前媒体 | 不能反向当作源码工程 |
| main 文档后续更新 | 说明补充 | 不覆盖已有同名 tag 或发行附件 |

不同目录可以存在，职责不能混用。评审先记录实际提交和版本；旧本地 checkout 的 origin/main 可能未刷新，不能由它推断远端不存在发行件。私有仓库匿名返回 404 也不能证明没有项目。

## 唯一发布入口

1. 修改版本、构建、审查与提交；工作树存在未提交内容或未跟踪笔记时，release 拒绝开始。
2. 从确切提交执行 git archive，开发机的忽略文件与 node_modules 不作为软件源进入快照。
3. 独立构建后核对明确发布范围、媒体路径/大小/哈希、源码隐私规则、版本及生成物；不从任意目录“全量打包”。
4. 在冻结包运行回归，并对 ZIP 再解压，严格核对文件集合、字节数和哈希；任何失败阻止成功发行件。
5. 输出 source-provenance.json 和验证回执，包含 commit、tree、版本及范围。SHA-256 校验内容一致性，不冒充签名或作者身份认证。
6. 上传后仍需独立回下载、验 SHA、临时 profile 升级/回退与原生 DSH 验收；本地门禁不能替代后半程。

`theme` 完整包始终为默认交付。显式 `--core` 是无画像的开发基础版，不会悄悄替换用户期待的完整皮肤。两个范围各自验证文件集合与降级行为。

## 收敛约束

当前先维护一个完整主题及其安装/恢复工具。增加新场景、动作或工具前，先把已知 P1、发布门禁与未验项处理清楚；已有候选数量不作为交付质量指标。新的付费素材制作另行约定单批预算，不由构建、测试或维护命令触发。
