# Kshine 的维护流程

## 一次改动

1. 从已知可用提交新建 `codex/` 功能分支，先说明问题和受影响宿主版本。
2. 修改源码并构建。运行自动化与相关开屏套件，再做本地预览。
3. 在临时 profile 检查安装、重复安装、失败恢复和卸载；在真实 DSH 记录冷启动、深浅、三场景、阅读、窄窗和图库。每项明确通过、失败或未测。
4. 核对来源、许可和白名单，检查 `git diff --cached`；用 GitHub 隐私邮箱提交，不提交运行数据。结构、安装与发布改动由另一个独立上下文复查，发现问题要补回归并复核，不以同一代理自述代替第二次检查。
5. 推送并查看 GitHub Actions 结果。CI 未通过时先修复，不能把“已上传”当作验收通过。

## 发布

- beta 用 `0.x.y-beta.n`；每个修改过的已安装运行版本使用新版本号。保留更新记录、兼容范围、已知问题和回滚说明。
- 完整主题是默认交付，包含用户生成并明确纳入作品的三组背景；保留许可和来源说明。个人图库与影片继续由用户外置管理。
- `node tools/set-version.mjs <版本>` 同步元数据、锁文件与文档源码版本块，构建注入 HUD 版本；verify 拒绝漂移。
- `node tools/release.mjs` 只接受干净 Git 提交，以 git archive 冻结源，构建、核媒体与隐私、执行回归、压缩并重新解压核对，最后才输出 ZIP、SHA-256 和验证回执。工作树脏、CI/浏览器失败或任何文件不符都不能发布。
- GitHub Actions 在 Windows 覆盖 Node 22.19 / 24，浏览器使用 Microsoft Edge。临时 profile 的 junction / 原子替换必须在语义正常的 Windows 环境跑；沙箱 EPERM 不等于代码通过，也不能用关闭 guard 让数字变绿。
- CI 新鲜运行结果与附件哈希应进入发布回执；不编造尚未存在的 CI 链接。下载到不同路径复测安装与卸载，确认数据目录的管理入口独立于源码目录。
- GitHub 版本附件需要人工确认版本、私有/公开范围和素材边界。稳定版需完成真实重启验收及至少一次其他机器试装；未测项目写进说明，不承诺全版本兼容。

## 宿主更新与回滚

DSH 更新后先在分支复核语义 DOM、标题栏/侧栏选择器和插件加载协议，再提高兼容声明。出现故障时优先恢复最后可用包，保留用户图库与视频；不要强行覆盖手动修改的管理区段。

持续维护由 Kshine 手动触发；项目没有后台监控、自动上传、自动更新或未经请求的计划任务。
